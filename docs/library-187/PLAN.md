# CloudSite 文件数量加载：Chrome 实测与优化方案

结论：主要缺陷在 CloudSite 文件库的读取与展示策略。页面把“已下载条目数”当作分类数量，每次刷新重新全量读取；显示完成后仍重复全量拉取。优化应在 CloudSite 建立可复用的目录读模型和统计快照，让首屏只读当前页，不让用户等待整库遍历。当前仅分析，未修改应用源码、生产配置或数据。

## 已验证事实

使用用户真实 Chrome 已登录标签页 `https://cloud.netioi.com/`，执行一次普通浏览器刷新，观测页面和 CDP Network 事件。没有调用刷新扫描、提交 Hint 或修改网盘文件。

| 观测 | 本次结果 |
| --- | --- |
| 初次文件列表读取 | 18个串行 GET `/api/v1/resources`，每页最多50条，whole_root=true |
| 接收条目 | 858条，343个文件、515个目录；目录最后在浏览器被丢弃 |
| 全部18页网络完成时间 | 从首个列表请求开始16.115秒；不等于首屏渲染时间 |
| 后台两轮完整重读 | 各18个请求，10.011秒、9.807秒；所有响应200 |
| 完整重读启动间隔 | 18.955、20.009秒；另见下一轮启动间隔10.005秒 |
| 页面最终数量 | 全部343、软件42、视频235、文档6、其他60 |
| 文件分页 | 浏览器把已下载数组按120个切片；网络仍预先读取整库 |
| 后台定时器 | 每10秒尝试全量重读，busy/quietRefresh等保护会跳过正在工作的轮次，并非每10秒必定完成一轮 |

因此，截图264→326等变化不能直接当作此期间新增了62个文件；本次实测支持“加载进度被展示成总数量”的解释。不能仅凭该现象确认真实网盘文件变化。

CDP最初读取返回truncated标记，导航及静态资源的完整事件链不作完整性声明；已观察到首个无cursor列表请求、18页响应和最后空cursor响应，随后读取未截断。原始证据只保留路径、参数名、时间、状态和数量，不保留凭据、绑定ID、游标或文件明细。首屏绘制、服务器SQL/IndexCore分段耗时为NOT_TRACKED。

Chrome实际加载的library.js SHA256为 `add73ea076bcff3f92ee58c58c15719393c0d83ea29d82003ba680f20e6989a0`；与本地v1.0.2源码按LF规范化后的SHA256一致。本地HEAD为 `9eb4111a705bc60d264c19a2a2cecfe6e0a9b255`。

## 根因与代码链

- `internal/producthttp/web/library.js:147`：refreshFiles取消请求、clearFiles清空列表及数量，再新建Catalog并调用loadWholeLibrary。
- `library.js:146`、`file-catalog.js:16`：循环读取全部分页，每轮最多4页且逐页await；每轮drawFiles重算分类并重建列表。
- `library.js:111`：ResourceDisplay.counts统计当前浏览器数组；全部数据尚未加载时，分类值就是部分计数。
- `library.js:116`：上下页按120个切片，只限制DOM展示，不限制网络读取。
- `library.js:200`及`:218`：每10秒尝试建立新Catalog并读完全部分页，即使没有展示变化；完成后才比较数组并替换。
- `library.js:10`：当前GET使用cache:no-store，不会直接复用浏览器HTTP缓存。
- `internal/product/reads.go:286`：CloudSite调用IndexCore Browse；`integrations/indexcore/client.go:159`在whole_root模式使用Q6 active清单，不是在页面请求中重新扫描真实OpenList。
- `product/reads.go:297`附近：对每条物理记录调用GetCopyByPhysicalIdentity；`store/postgres/catalog_repository.go:353`执行一条精确SQL，形成逐条数据库查找。这个源码路径是额外开销，线上数据库实际查询数量、占比和耗时未采集，不能用源码推算值冒充实测。

## 推荐的最终行为

刷新页面后，在身份与可见范围确认后立即展示最近一次成功发布的分类统计和首屏文件；后台查询变化。文件有变化时保留旧列表，完成核对后更新数量和受影响内容，保持当前分页、搜索、详情和播放状态。读取失败保留旧结果并提示未更新；不得清零或将部分结果当成完整文件库。

冷启动没有任何有效快照时，先返回有界首屏，分类显示“统计中”或短横线，不用0表示未知。完整基线在后台建立；不让首个用户请求同步承担整库构建。

## 模块设计与依赖

| 模块 | 单一职责及接口 |
| --- | --- |
| CatalogProjection | CloudSite派生读模型，按binding/root/resource身份保存可展示文件、分类、路径及产品展示覆盖；复用IndexCore已验证事实，不写Canonical。 |
| CatalogSync | 后台构建完整基线，复用现有Q8消费能力增量更新；游标和更新在事务中提交，重复事件幂等，缺口触发后台重建。每个范围单飞，避免每用户建同步器。 |
| LibraryReadService | 已授权范围内查询分类统计、筛选和文件分页，输出revision、updated_at、完整性及next_cursor；不因首页读取触发整库遍历。 |
| HTTP接口 | 可用一个library首屏接口返回统计+50条文件；后续按cursor/category/search请求。独立版本检查可返回304，认证/授权仍每次执行。 |
| 前端控制器 | 展示最近成功结果，按需分页，后台获取变化；loading状态独立于总数，保留旧内容与交互位置。 |

可先在CloudSite后台缓存现有整库读取结果，持久保存最近成功快照以跨重启复用；再接Q8增量维护。不能用“把整库读取从浏览器移到同一个同步HTTP请求”替代后台构建，那仍会把冷启动耗时交给用户。

现有Copy表不一定覆盖所有PHYSICAL_ONLY文件，不能直接COUNT(copies)当作文件库总数。派生读模型必须包含当前接口允许展示的物理文件，并复用产品分类与隐藏策略。

统计与分页需要明确的数据集版本：同一已发布revision生成统计和首屏；分页关联其数据集，版本过期时提示并保留旧内容再切换。多Root范围的版本包含各Root检查点和产品展示版本，不假称跨Root瞬时全局快照。

## 实施顺序

1. **先控制反复重读与闪烁。** 取消每个浏览器10秒整库重读，改为轻量revision检查；刷新/异常保留最近成功结果。后端按页批量查询Copy，保留精确物理身份与错误语义。减少仅为隐藏布局而创建的DOM。
2. **完成统计快照和真正分页。** 服务端提供统计与首屏，浏览器只加载所选页；分类和搜索也在服务端作用于完整可见数据集，不能停留在已加载子集。
3. **接入增量更新。** 复用Q8维护展示读模型和统计，检测到展示内容变化才发布新revision。无变化只检查版本，有变化获取受影响页或增量。跨页排序移动可重新取当前页，避免每次重下全部文件。

第一步可减少后台请求与刷新闪烁，但仅做前端保留旧数据不能完全解决硬刷新、全局数量和搜索问题，必须完成第二步。

## 缓存和正确性约束

- 文件新增/确认删除/类型或分类变更/跨主库与云下载范围移动，以及产品别名、分类、隐藏、Binding和访问范围变化，都要触发对应更新。目录移动需处理后代范围，不能只看一条事件做简单加减。
- 未变化的扫描、纯观察时间更新，不应让所有页面缓存失效。不能只用Canonical generation作为缓存失效条件；还要覆盖实际展示和授权变化。
- 所有缓存键包含有效可见范围与版本；统计不得跨用户/租户/Binding误共享。若采用浏览器持久缓存，必须在认证及范围核验后使用，退出、账号切换和授权失效时清理。
- GET认证接口继续no-store。只有经过授权设计的统计/分页接口采用private ETag与条件请求；不要全站删除no-store，也不要公开缓存私有元数据。
- 部分读取、网络失败、Journal缺口都不是删除证据；新快照未完整验证前不能覆盖旧成功快照。
- 文件内容访问、下载和分享仍走原有实时鉴权与身份核对，缓存列表不授予访问权限。
- Q8之外的产品展示修改也要推进展示revision；纯IndexCore游标不能独自代表整个网站的可见状态。

## 验收目标（尚未实施，非实测提升）

| 场景 | 验收条件 |
| --- | --- |
| 有有效快照的硬刷新 | 身份核验后1–2个文件库数据请求取得统计+首屏；不要求先读18页，分类不从0累加。认证请求另算。 |
| 无文件变化 | 轻量版本检查，不重复下载全部分页；明确区分缓存命中、304与真实源请求。 |
| 少量增删改 | 更新对应统计/当前页，列表不清空，保留交互状态。 |
| 冷启动/缓存丢失 | 有界首屏可用、统计未知明确显示，后台单飞建立基线。 |
| 读取失败/取消/乱序响应 | 保留旧成功结果，不误清空、串账号或回退版本。 |
| 数据正确性 | 分类合计与同版本可见文件总数一致；云下载分区、隐藏覆盖、目录移动、权限变更正确。 |
| 性能 | 分别记录认证耗时、首屏API、绘制、SQL次数/耗时和后台同步成本；可先设认证完成后首屏数据P95<1秒为目标，需真实测量后验收。 |

没有证据支持提高IndexCore Reader或开启F4能修复这个前端加载问题。本方案不要求改Kernel、Canonical、Journal语义或增加Canonical写入进程。
