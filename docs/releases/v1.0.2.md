# CloudSite 1.0.2

Maintenance patch for [Issue185](https://github.com/nathanxiangang-web/cloudsite/issues/185).

## Behavior and incident

Cloud downloads no longer have a website lifetime download-count cap or a
per-account submission/concurrency cap. The download page says 下载次数不限 and
shows the number of submitted operations. Existing accounts receive this policy
immediately, including accounts with customized legacy quota rows.

The incident was caused by two RECOVERY_REQUIRED tasks consuming both of an
account's two nonterminal-task slots. They could not complete automatically, so
every new submission returned CONCURRENCY_LIMIT despite no normal work running.
The lifetime limit of 100 was a separate restriction, not the screenshot's cause.

## Module boundaries and extension rules

- ProductAdmissionRepository owns atomic owner authorization, per-owner ledger
  serialization and persistence. It no longer checks either legacy cap. Retain
  the quota row and row lock for FK, idempotency and account-deletion safety.
- Product UsageDTO explicitly returns unlimited=true and zero operation_limit,
  concurrency_limit and remaining. Those zero fields mean no cap only when the
  flag is true; used and in_flight remain real historical counts, including
  recovery records. AdmissionService validates the coherent DTO contract.
- downloads.js renders unlimited usage and supports older finite DTOs during
  rollout. The UI never chooses the admission policy or automatically submits.
- The existing serial Worker, provider start reservation, unknown-result fence,
  retry budget, immutable operation replay and authentication remain intact.
  Website admission limits are distinct from actual provider execution limits.

Do not delete/requeue uncertain historical tasks, rewrite their provider state,
reset usage, or raise legacy limits to a large fake allowance. Future policy
changes belong in the admission module and its explicit usage contract, with
independent domain, PostgreSQL and UI contract tests.

## Validation and deployment

Regression coverage submits 105 operations with legacy limits set to zero/one,
including two RECOVERY_REQUIRED tasks. Replay preserves the original pair and
no provider call occurs. Concurrent distinct operations and same-key replay,
authorization, rollback and account-deletion guards remain covered. UI tests
verify that unlimited usage is not displayed as an exhausted zero allowance.

Schema remains20; no migration or production quota/Manifest/Job rewrite is
needed. Publish only after exact-main CI succeeds. Deploy only the product image
after a backup and isolated PostgreSQL16 restore verification. Preserve v1.0.1
and the prior Compose for rollback. Verify health, served assets, unchanged
historical task/ledger/account/session records and unrelated containers.

Historical recovery records remain recoverable incidents; this patch removes
their ability to prevent new submissions and does not claim their downloads
have completed or repair remote-provider availability.
