# CloudSite 1.0.1

Maintenance fix requested on 2026-11-02: account deletion must be direct and
permanent, rather than an account-disable/tombstone workflow.

## User-facing behavior

Each ordinary-user row has a Delete action. One confirmation names the account
and explains that deletion cannot be undone; there is no checkbox or separate
management-form step. Disable and restore actions are removed from the UI.
Completed action receipts no longer leave the page locked on the next visit;
an outstanding receipt is reconciled by GET, never by replaying the command.

## Module contract

AdminLists supplies the selected row through a narrow callback. AdminOperations
owns confirmation, actor/session fencing and the single existing DELETE command.
The PostgreSQL lifecycle module retains its actor, USER-only target, version,
account-lock, terminal-task and Manifest/Job coherence guards. A dedicated
deleteAccount helper performs the permanent removal inside the audited action
transaction and a rollback-safe savepoint.

Deleted data: the product account/password hash, website sessions, account-owned
share links/grants, private admission ledger and account quota. Retained data:
historical Manifest/Job/provider-task rows, their original UUID ownership and
ADMIN audit intent/results. No storage file, canonical resource or provider task
is deleted or retried. A later account using the same login receives a new UUID
and cannot inherit the deleted account's tasks or shares.

Legacy enable/restore result codes and backend compatibility remain available
for old receipts/deployments; neither is a UI action. A physically removed
account cannot be restored. Existing soft-deleted USER records can be explicitly
permanently deleted; this release does not purge any production account itself.

## Validation and deployment

Frontend checks cover cancellation, direct row deletion, a single versioned
command, duplicate clicks, UNKNOWN receipt fencing and terminal receipt cleanup.
PostgreSQL checks cover actual row/session/share/ledger removal, stable audit
replay, fresh login identity, rollback and concurrent admission protection.
The complete CI suite remains required before release.

Schema remains 20 with no migration. Deployment replaces only the product image
using the established backup/isolated-restore/health gates. Keep v1.0.0 and its
compatible image available for code rollback. Rolling code back does not restore
accounts intentionally deleted after deployment; never overwrite newer data with
an old backup without a separate recovery decision.
